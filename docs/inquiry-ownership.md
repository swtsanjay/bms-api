# Inquiry ownership

`inquiries.user_id` identifies a legacy `users` account. `inquiries.commerce_customer_id` identifies a Vastriqo `vsq_customers` account. `ownership_source` records which authentication path verified a new submission (`LEGACY_FRONT`, `COMMERCE_CUSTOMER`, or `GUEST`). `inquiries.assigned_staff_id` identifies the Salesman assigned to handle the inquiry; it does not grant customer ownership. Guest inquiries have both customer ownership columns null.

The ownership migration adds nullable columns and does not backfill them. An older inquiry with a legacy `user_id`, or with only matching email or phone details, may have originated from a commerce customer, a legacy user, or a guest. Its null `ownership_source` keeps it available to authorized staff in the admin inquiry workflow, but out of both commerce and legacy customer histories. A matching numeric ID across the two customer tables does not establish identity.

For a customer asking about an older inquiry, staff can continue handling it through the existing admin assignment workflow. The customer can also submit a new inquiry while signed in, which will have verified commerce ownership. Restoring history for an old row requires a separate, audited support process: verify control of the current commerce account and independent evidence of the original inquiry, review conflicting legacy ownership or other claimants, then have an authorized operator explicitly link that specific row. A verified commerce claim must set `commerce_customer_id` and `ownership_source = 'COMMERCE_CUSTOMER'` while clearing any ambiguous `user_id`; a verified legacy claim must set `ownership_source = 'LEGACY_FRONT'` only for the confirmed legacy user. Do not use a public self-claim endpoint or infer ownership from email, phone, `user_id`, or a form field. No automatic claim or manual linking endpoint is included in this change.
